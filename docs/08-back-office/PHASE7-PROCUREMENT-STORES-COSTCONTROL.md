# فاز ۷ — انبار، خرید، تدارکات و کاست کنترل (سند تحلیل و پیاده‌سازی)

> موج ۲ — بر اساس نقشه راه جامع (بخش‌های ۷.۵ و ۷.۶). مهاجرت مستقل:
> `20261124010000_procurement_stores_phase7`.

## ۱. هدف و تصمیم‌های MVP

چرخهٔ کامل «درخواست کالا → سفارش خرید → رسید → گردش انبار → مصرف منو → انبارگردانی →
واریانس» با **میانگین موزون** (سیاست مصوب این پروژه؛ FIFO به موج بعدی) و مرجع مشترک
سند انبار/مالی: هر گردش قطعی انبار، ردّی در `stock_movements` با refModule/refId دارد و
رویداد پولی هم‌تراکنشِ همان گردش، سند مالی می‌زند — دو دفتر هرگز جدا نمی‌شوند.
**تعمداً موکول به موج بعدی:** UnitConversion چندسطحی (فعلاً ضریب تبدیل واحد خرید→مصرف
در هر قلم)، بچ/تاریخ انقضا در سطح سطر رسید (فیلد موجود، گزارش بعداً)، حواله برگشت و
ضایعات به‌صورت گردش ADJUST/WASTE ساده، SupplierInvoice جدا (GRN مبنای بدهی است).

## ۲. موجودیت‌ها

| موجودیت | نقش |
| --- | --- |
| `Warehouse` | انبارها (غذایی/سردخانه/شارژ آشپزخانه/نوشیدنی/خانه‌داری/لاندری/تجهیزات/ضایعات) |
| `StockItem` | قلم با واحد خرید/مصرف + ضریب تبدیل، حداقل، میانگین موزون و موجودی جاری |
| `StockMovement` | تنها منبع حقیقت موجودی: IN/OUT/ADJUST_IN/ADJUST_OUT/WASTE با مرجع |
| `Supplier` | تأمین‌کننده با حساب ledger پیش‌فرض ۲۱۰۱ |
| `PurchaseRequisition`(+Line) | درخواست کالا: DRAFT→SUBMITTED→APPROVED→CONVERTED |
| `PurchaseOrder`(+Line) | سفارش خرید: DRAFT→APPROVED→PARTIAL→RECEIVED/CANCELED با qtyReceived هر سطر |
| `GoodsReceipt`(+Line) | رسید خرید (کامل/جزئی) → گردش IN + بدهی + سند |
| `StockCount`(+Line) | انبارگردانی با variance سطر به سطر → اصلاحی + سند |

قواعد غیرقابل نقض: موجودی فقط از گردش قطعی؛ موجودی منفی فقط با مجوز صریح (فیلد
allowNegative قلم — مصرف آشپزخانه پیش‌فرض مجاز و در گزارش واریانس دیده می‌شود، حوالهٔ
دستی بدون مجوز رد می‌شود)؛ اصلاح موجودی فقط با گردش ADJUST و سند؛ مبلغ‌ها ریال صحیح و
مقادیر کمی Decimal(12,3).

## ۳. رویدادها و سند خودکار

- `procurement.po.approved` (غیرپولی) — تعهد خرید؛ بدون سند مالی.
- `procurement.grn.received` (**پولی**) — بدهکار ۱۳۰۱ موجودی (خالص) + ۲۲۰۴ مالیات خرید،
  بستانکار ۲۱۰۱ تأمین‌کننده (کل). میانگین موزون همان تراکنش به‌روز می‌شود.
- `inventory.consumption.posted` (**پولی**) — بدهکار ۵۱۰۱ COGS، بستانکار ۱۳۰۱؛ توسط ماژول
  stores از رویداد غیرپولی `restaurant.order.served` فاز ۶ تولید می‌شود (مصرف به بهای میانگین).
- `inventory.adjustment.posted` (**پولی**) — کسری: بدهکار ۵۱۰۴ هزینه مغایرت/ضایعات، بستانکار ۱۳۰۱؛
  اضافه: عکس آن.

## ۴. زنجیرهٔ کاست کنترل (۷.۶)

سرو سفارش رستوران → `restaurant.order.served` → مصرف‌کنندهٔ stores: برای هر قلمِ مندارِ
رسپی‌دار، به‌ازای هر سهم: گردش OUT به مقدار `qty × qtyPerPortion` (با تبدیل واحد) و بهای
میانگین؛ جمع ارزش → رویداد مصرف → سند COGS. گزارش تئوریک/واقعی: تئوریک از سفارش‌های
سرو‌شده × فرمول رسپی، واقعی از گردش‌های OUT دوره؛ انحراف مقداری و ریالی. نسخه‌بندی
رسپی با فیلد version و تاریخچه در snapshot قلم‌ها.

## ۵. API نسخه‌دار و مجوزها

`/api/v1/procurement/suppliers|requisitions|orders|receipts`، `/api/v1/stores/items|
movements|counts|cost-control|reorder` — مجوزها: `procurement.view/manage/receive`،
`stores.view/manage/count`، `restaurant.view/order/kds`، `pos.discount`.

## ۶. تست پذیرش (F7-T1…T6)

T1 ساخت قلم/انبار/تأمین‌کننده؛ T2 درخواست→تأیید→تبدیل به PO؛ T3 PO→GRN جزئی: موجودی،
میانگین موزون و سند (۱۳۰۱/۲۲۰۴/۲۱۰۱) + وضعیت PARTIAL؛ T4 تکمیل رسید→RECEIVED؛
T5 سرو سفارش رسپی‌دار → گردش OUT با تبدیل واحد + سند COGS؛ T6 انبارگردانی با کسری →
گردش ADJUST + سند ۵۱۰۴/۱۳۰۱ + گزارش تئوریک/واقعی.
