# سند ۰۵ — مشخصات API و قراردادهای بین‌ماژولی

> فاز ۰ — قواعد حاکم بر همه APIها. مستندات زنده: OpenAPI خودکار از کد (NestJS) در /docs مسیر اجرایی.

## ۱. اصول کلی

1. **REST منبع‌محور** با OpenAPI ۳ تولیدشده از کد؛ هر تغییر قرارداد = تغییر نسخه.
2. **نسخه‌دار در URL:** `/api/v1/...` — تغییر شکستن (breaking) فقط با نسخه جدید؛ نسخه قدیمی حداقل
   دو دوره حذف تدریجی پشتیبانی می‌شود.
3. **احراز هویت:** JWT کوتاه‌عمر + Refresh چرخشی؛ MFA برای نقش‌های حساس؛ نقش‌ها و مجوزها در
   هر درخواست سمت سرور اعتبارسنجی می‌شوند (هرگز فقط UI).
4. **Idempotency:** همه متدهای حالت‌تغییرده حساس با هدر `Idempotency-Key`؛ کلید تکراری = همان
   پاسخ قبلی، بدون ثبت مجدد.
5. **صفحه‌بندی:** cursor-based برای فهرست‌های بزرگ (`?cursor=&limit=` حداکثر ۱۰۰)؛ مرتب‌سازی صریح.
6. **زبان:** هدر `Accept-Language: en|fa`؛ خطاها و پیام‌ها دوزبانه؛ تاریخ‌ها ISO-8601 UTC.

## ۲. ساختار پاسخ و خطا

```json
// موفقیت
{ "data": { }, "meta": { "page": {}, "requestId": "uuid" } }
// خطا — همیشه با کد ماشین‌خوان و پیام انسانی دوزبانه
{ "error": { "code": "FOLIO_ALREADY_SETTLED",
             "message": "Folio is already settled / فولیو پیش‌تر تسویه شده",
             "details": [ ], "requestId": "uuid" } }
```

کدهای وضعیت: 200/201/204 موفق | 400 اعتبارسنجی | 401 احراز | 403 مجوز | 404 پیدا نشد |
409 تعارض وضعیت (مثل تسویه دوباره) | 422 قاعده کسب‌وکار | 429 محدودیت نرخ | 5xx خطای سرور
(هیچ جزئیات داخلی/اسکیمای دیتابیس در پاسخ افشا نشود).

## ۳. قرارداد رویدادهای دامنه‌ای (RabbitMQ)

- نام‌گذاری: `<context>.<entity>.<action>` مثل `booking.reservation.confirmed`،
  `pos.order.served`، `inventory.goods.issued`، `payroll.run.approved`.
- پیام: `envelope = { eventId: UUID, occurredAt, producer, idempotencyKey, payload, version }`.
- تحویل: **at-least-once** + مصرف‌کننده تکرارپذیر (inbox)؛ شکست→ صف بازپخش؛ شکست مکرر→ DLQ + هشدار.
- انتشار فقط از طریق **Outbox** در همان تراکنش دامنه (هیچ رویداد گم‌شده مجاز نیست).

## ۴. فراخوانی درون‌ماژولی (درگاه سرویس)

هر ماژول فقط «قرارداد منتشرشده» ماژول دیگر را صدا می‌زند (interface نسخه‌دار در پکیج contracts)؛
فراخوانی مستقیم repository ماژول دیگر در بازبینی کد رد می‌شود.

## ۵. نمونه قرارداد مسیرهای هسته (v1)

| متد/مسیر | شرح | نکته |
|---|---|---|
| POST /api/v1/auth/login | ورود | MFA نقش حساس |
| GET /api/v1/rooms?status= | فهرست اتاق‌ها | صفحه‌بندی |
| POST /api/v1/reservations | ایجاد رزرو | کنترل ظرفیت؛ 409 در تعارض |
| POST /api/v1/checkins | ثبت ورود | شناسنامه + امضا |
| GET /api/v1/folios/{id} | فولیو مهمان | مجوز نقش‌دار |
| POST /api/v1/folios/{id}/charges | ثبت شارژ | منبع = ماژول مالک خدمت |
| POST /api/v1/folios/{id}/settle | تسویه | Idempotency الزامی |
| POST /api/v1/pos/orders | ثبت سفارش | رویداد pos.order.placed |
| POST /api/v1/inventory/movements | گردش انبار | اعتبارسنجی مانده |
| POST /api/v1/journal-entries | ثبت سند | ۴۱۴ فیلد + اتمیک + Idempotency |
| POST /api/v1/moadian/invoices | صدور و ارسال صورتحساب | صف پایدار + بازپخش |

## ۶. قواعد تست API

- هر اندپوینت: تست واحد + تست یکپارچگی + تست مجوز (نقش مجاز/غیرمجاز) + تست Idempotency.
- قراردادها با اسنپ‌شات OpenAPI در CI کنترل می‌شوند (تغییر ناخواسته = شکست بیلد).
- تست بار: مسیرهای کلیدی با ۵۰ کاربر هم‌زمان (آستانه پاسخ ۹۵٪ < ۲ ثانیه).
